## 1. What is WebSocket?

WebSocket is a **communication protocol** that provides a persistent, full-duplex connection between a client and server.

The important concepts are:

* **Persistent** → connection stays open
* **Full-duplex** → both client and server can send data
* **Real-time** → server can push data immediately
* **Low overhead** → after the initial handshake, messages don't require a new HTTP request

## 2. HTTP vs WebSocket

### HTTP

Normal HTTP follows a request-response model:


Client
   |
   | HTTP Request
   v
Server
   |
   | HTTP Response
   v
Client


For example:

http
GET /messages


Server:

json
[
  "Hello",
  "How are you?"
]


If the client wants new data, it needs another request.


Client → GET /messages
Server → messages

Client → GET /messages
Server → messages

Client → GET /messages
Server → messages


This is called **polling**.

## 3. WebSocket

With WebSocket, the client establishes a persistent connection.


Client ═════════════════════ Server
       Persistent connection


After the connection is established, both sides can send messages.


Client → Server
Client ← Server
Client → Server
Client ← Server
Server ← Client
Server ← Client


The server does not need to wait for the client to make another HTTP request.

There are two common WebSocket schemes:


ws://

## 5.1 `ws://`

`ws://` means normal, unencrypted WebSocket.

Example:

javascript
const socket = new WebSocket(
  "ws://localhost:8080"
);


It is similar to: http://

It is commonly used during local development.

## 5.2 `wss://`

`wss://` means **WebSocket Secure**.

Example:

javascript
const socket = new WebSocket(
  "wss://example.com/socket"
);


It uses TLS encryption.

Similar relationship:
http  → https
ws    → wss


### Comparison

| Protocol | Encryption        |
| -------- | ----------------- |
| `ws://`  | No TLS encryption |
| `wss://` | TLS encrypted     |

For production applications, `wss://` is normally preferred.

# 7. WebSocket starts with HTTP

This is one of the most important concepts.

WebSocket does **not** initially start as a completely separate connection protocol.

The browser first sends an HTTP request asking the server to upgrade the connection.

Example:

http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: abc123...
Sec-WebSocket-Version: 13


The important headers are:

http
Upgrade: websocket
Connection: Upgrade


The client is essentially saying:

> "I want to upgrade this connection from HTTP to WebSocket."

# 8. `101 Switching Protocols`

If the server accepts the upgrade, it responds:

http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...


`101` means:

> The server agrees to switch protocols.

The flow becomes:


HTTP
 ↓
WebSocket Handshake
 ↓
101 Switching Protocols
 ↓
WebSocket

HTTP status codes include:


200 → OK
201 → Created
400 → Bad Request
401 → Unauthorized
403 → Forbidden
404 → Not Found
500 → Internal Server Error


`101` means:


101 Switching Protocols


For WebSocket:


Client:
"Can we upgrade to WebSocket?"

Server:
"Yes."

101


After the handshake, the communication is no longer normal HTTP request/response traffic.

Instead:


Client ⇄ WebSocket ⇄ Server

# 11. `Sec-WebSocket-Key`

# Sec-WebSocket-Key is generated by the WebSocket client during the initial WebSocket handshake, before the server sends the 101 Switching Protocols response.

The browser generates a random value:

http
Sec-WebSocket-Key: random-value

It helps the client and server verify that the response is actually a valid WebSocket handshake.

You normally do not implement this manually. The browser and WebSocket library handle it.

it is generated for each WebSocket connection attempt, not once for the lifetime of the application

// Connection 1
new WebSocket("wss://example.com");
// → Key A

// Connection 2
new WebSocket("wss://example.com");
// → Key B

When you write:

const socket = new WebSocket("wss://example.com"); // the browser's WebSocket implementation starts the connection process.

new WebSocket() → browser generates Sec-WebSocket-Key → sends HTTP Upgrade → server returns 101 + Sec-WebSocket-Accept → WebSocket begins.

# 13. WebSocket Frames

WebSocket doesn't simply send raw messages directly over TCP.

It divides communication into **frames**.

Conceptually:


+----------------------------------+
| WebSocket Frame                  |
+----------------+-----------------+
| Header         | Payload         |
+----------------+-----------------+


A frame contains information such as:

FIN
Opcode
MASK
Payload Length
Masking Key
Payload

# 14. Why does WebSocket need framing?

TCP provides a byte stream.

TCP doesn't understand:
Message 1
Message 2
Message 3


WebSocket adds framing on top of TCP.

Conceptually:


TCP Stream
────────────────────────────────────

WebSocket:

+---------+  +---------+  +---------+
| Hello   |  | World   |  | Bye     |
+---------+  +---------+  +---------+
   Frame        Frame        Frame


Framing allows WebSocket to identify the boundaries and type of protocol data.

# 15. Important WebSocket frame fields

## FIN

`FIN` indicates whether the frame is the final fragment of a message.

FIN = 1 //means the current frame completes the message.


## Opcode

The opcode tells us what type of frame it is.

Important opcodes:
1  → 
2  → Binary
8  → Close
9  → Ping
10 → Pong

## MASK

Client-to-server frames are masked.

The browser handles masking automatically.

You generally don't manually implement this when using:

javascript
new WebSocket(...)

## Payload Length

Specifies the size of the payload.

## Masking Key

Used to mask client-to-server payload data.

Again, the browser handles this automatically.

# 17. Frame vs Message

A **message** and a **frame** are related but not necessarily identical.

A WebSocket message can consist of one or more frames.

For normal application development, you usually don't need to deal with fragmentation manually.

You simply do:

javascript
socket.send("Hello");


and receive:

javascript
socket.onmessage = (event) => {
  console.log(event.data);
};


The WebSocket implementation handles the underlying frames.

# 18. Browser WebSocket API

The browser provides a built-in WebSocket API.

javascript
const socket = new WebSocket(
  "ws://localhost:8080"
);


Important events:
onopen
onmessage
onerror
onclose

# 19. `onopen`

Runs when the connection is successfully established.

javascript
socket.onopen = () => {
  console.log("Connected");
};


You can send an initial message:

javascript
socket.onopen = () => {
  socket.send("Hello Server");
};

# 20. `onmessage`

Runs when the server sends a message.

javascript
socket.onmessage = (event) => {
  console.log(event.data);
};


If the server sends:

json
{
  "type": "message",
  "": "Hello"
}


The client can parse it:

javascript
socket.onmessage = (event) => {
  const data = JSON.parse(event.data);

  console.log(data.);
};

# 21. `onerror`

Handles WebSocket errors.

javascript
socket.onerror = (error) => {
  console.error(
    "WebSocket error:",
    error
  );
};


Do not depend only on `onerror`.

You should also handle:

javascript
onclose


because a connection can close for many reasons.

# 22. `onclose`

Runs when the connection closes.

javascript
socket.onclose = () => {
  console.log("Disconnected");
};


You can inspect the close event:

javascript
socket.onclose = (event) => {
  console.log("Code:", event.code);
  console.log("Reason:", event.reason);
};

# 23. WebSocket `readyState`

WebSocket has four connection states.

javascript
socket.readyState


Values:


0 → CONNECTING
1 → OPEN
2 → CLOSING
3 → CLOSED


You can check:

javascript
if (
  socket.readyState === WebSocket.OPEN
) {
  socket.send("Hello");
}

# 39. Challenges with WebSockets

WebSockets are powerful, but production systems have several challenges.
1. Connection management
- Connections can drop unexpectedly.
- Clients may switch networks or go offline.
- You need reconnection and retry logic.

2. Scalability
- A WebSocket connection stays open, unlike a typical HTTP request.
- Thousands/millions of concurrent connections can consume significant memory and file descriptors.
- Load balancing requires special handling, often with sticky sessions or shared connection state.

3. Heartbeats and dead connections

A connection can appear open even when the other side is no longer reachable.
Ping/pong or application-level heartbeats are commonly used to detect stale connections.

4. Backpressure
A server can produce messages faster than a client can consume them.
Without limits, queues can grow and cause high memory usage.
You may need buffering limits, message dropping, or rate limiting.

5. Horizontal scaling
With multiple WebSocket servers, a client connected to server A may need messages generated on server B.
A shared broker such as Redis Pub/Sub, Kafka, or another messaging system is often introduced.

A typical production architecture
             ┌──────────────┐
Clients ────►│ Load Balancer│
             └──────┬───────┘
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   WebSocket Server 1   WebSocket Server 2
          │                   │
          └─────────┬─────────┘
                    ▼
             Message Broker
                    │
                    ▼
              Application
                 Servers
